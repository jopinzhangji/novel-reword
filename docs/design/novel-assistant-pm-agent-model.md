# 小说助手：PM 式多智能体与记忆体组织（讨论稿）

**文档类型**：L2 概念方案（与 [DESIGN.md](../../DESIGN.md)、[author-agent-harness.md](./author-agent-harness.md) 并列讨论；**非**当前代码实现的逐条映射）  
**版本**：2026-04-09（共识修订）  
**目的**：用「产品管理 / 项目 / 专项」隐喻，统一描述**长期记忆**、**多智能体分工**与**作者在环 Harness**，便于评审与迭代。

---

## 1. 我们要解决什么问题

- **作者在环**需要**一个**对话主体（统一交互面），但小说生产涉及**设定、大纲、多角色、多范围、检索与写回**，单靠一个「大模型 + 长 prompt」会失控。  
- **长期记忆**既要有**跨小说、可复用的能力**（通用助手、通用工具），又要有**作品隔离**（某本书的角色弧、私密记忆、该书专属设定）。  
- 现有仓库已有：**编排器、角色/范围 Agent、设定研究 Agent、Harness（分类→检索→组装）**（见 DESIGN / TECH）。本方案把这些**收束到一条可讲清的管理故事线**：**PM（产品负责人）→ 小说（项目）→ 专项智能体（含角色）**。

---

## 2. 核心隐喻（三层）

| 层级 | 隐喻 | 在本系统中的含义 |
|------|------|------------------|
| **产品 / 产品线** | 整个「小说助手」这一产品 | 全局配置、通用智能体、跨作品策略、账号级偏好（若未来有） |
| **项目** | 单部 **小说**（`current_novel` / 作品目录） | 该书的世界、大纲、正文、该书级记忆与该书专属智能体注册表 |
| **任务 / 专项** | 一次具体工作流 | 如：本回合写作、设定审阅、某角色成长检查、大纲对齐；由 PM **派单**给对应专项能力或 Agent（小说侧能力**按需加载**，见 §4.2） |

**PM（Product Manager 智能体）**：与作者**统一交互**的主对话智能体（可对应「作者在环」对外的**单一入口人格**）。它不代替所有专业劳动，而是：

1. **理解**作者意图与当前阶段（与 Harness **Classifier** 一致方向）；  
2. **决定**要不要拉材料、派哪类「子智能体」干活（与 **RetrievalRouter / 策略包** 一致方向）；  
3. **汇总**结果再呈现给作者（与 **Handler + PromptAssembler** 一致方向）。

#### PM 与人格：可多阶段换「人格」，仍统一理解意图

- **允许**在**不同阶段**使用**不同对外人格**（如：设定阶段偏策划、正篇阶段偏编辑），以改善体验与提示词聚焦。  
- **不变**的是：**同一 PM 逻辑身份** + **Harness 统一入口**；作者仍感知为**一个助手**，而非多个无关聊天窗口。  
- **目标能力**：在**阶段切换**（`phase` / 子状态变化）时，**自动**切换适配的 system / 策略包，并**延续**对作者长期意图与本书上下文的理解（依赖 **digest、联合记忆摘要、匿名偏好**，而非仅靠当轮字符串）。  
- 实现上仍是：**同一 LLM 多角色模板** 或 **多步调用**；「换人格」= **策略包 + 可选人设语料** 切换，**不**等于换账号或换产品。

> **注意**：PM 是**逻辑角色**，实现上可以是**同一 LLM 多 system 提示**、**多调用**或**未来独立模型**；先定**职责边界**，再定工程形态。

## 3. 长期记忆：三种「记忆体」

为避免「所有东西塞进一个向量库」的含糊表述，建议区分三类（可与现有 `memory/`、`book/`、`author_interaction_state` 等**渐进对齐**）：

### 3.1 联合记忆体（Joint / Shared）

- **谁用**：多个智能体**只读或受控写**的**同一份**结构化或半结构化存储。  
- **内容示例**：世界规则摘要、已确认的大纲节拍、**非剧透级**的时间线锚点、跨角色可见的「正史」事件条目。  
- **特点**：**强一致性**要求高；写入常带**门禁**（作者在环确认、Harness Verifier）。  
- **与 DESIGN 对齐**：更接近 **Scope 事件簿、世界状态** 等「单一事实源」类数据。

### 3.2 智能体内置记忆体（Private / Agent-scoped）

- **谁用**：**单个**角色 Agent、单个范围 Agent 等**私有**记忆库（DESIGN 已写「分库存储、互不共享」）。  
- **内容示例**：角色关系、情感、该角色视角下的事件提炼、目标与动机。  
- **特点**：**可演进**、可冲突（再由编排器/世界协调者裁决）；检索时**默认只注入所属 Agent** 的上下文。

### 3.3 通用能力记忆体（Cross-novel, capability-level）

- **谁用**：**不绑定某一本书**的「助手侧」能力沉淀。  
- **当前共识（默认）**：**仅匿名偏好**——例如文体节奏、常用指令习惯、界面级选项；**不得**默认存储可还原具体作品剧情、可识别个人隐私的明文。  
- **后续扩展**：在匿名偏好跑通、合规与退出策略明确后，再评估是否增加「可关断的」更强跨书能力（单独规约）。  
- **与 A/B 书隔离**：默认仍须保证 **A 书正文与角色细节不得写入 B 书上下文**；跨书仅走 **匿名 / 统计级** 通道。

**一句话**：**联合记忆 = 作品内共识事实；内置记忆 = 某 Agent 主观与演进；通用记忆 = 当前默认仅匿名跨书偏好，其余慎扩**。

## 4. 智能体拓扑：PM → 小说管家 → 专项 Agent

在「产品 → 项目」框架下，建议**显式**拆两类「下属」：

### 4.1 通用智能体（跨小说可复用）

- **设定研究、检索、摘要、大纲对齐、节拍检查**等：模板与工具链可复用；**实例**仍绑定**当前 `data_root`**，避免串本。  
- **实现提示**：对应代码里多为 **Orchestrator 调用的领域函数 + LLM**，而不是「每本书一个独立进程」。

### 4.2 小说专属智能体（Novel-scoped）

- **「小说管家」能力（现阶段共识）**：**不**单独做一个常驻**独立智能体**；以 **Orchestrator + 配置 + `novel_root` 上下文** 为主，在需要本书级编排、进度、门闩时 **按需加载**（模块、提示词片段、策略包）。若未来体验证明需要稳定「人格」，再评估是否升格为独立角色（见 **§8 阶段 D**，可选实验）。  
- **角色演进智能体（Character Agent）**：DESIGN 已定义：**每主要角色一个 Agent**，私有记忆与演进；**归属本书**，在本书的「角色注册表」下管理。  
- **范围 Agent**：本书某 **Scope** 的事件与因果；同样归属本书。

**层级关系（管理线）**：

```text
作者
  ↔  PM（统一交互 / Harness 入口；可阶段换人格，见 §2）
        ├─ 通用服务 + 全局工具（记忆搜索、知识库、联网等，见 §4.3）
        └─ 按当前小说 (novel_id) 挂载
              ├─ 本书级能力（按需加载「管家」逻辑，非独立 Agent）
              ├─ 范围 Agent × N
              └─ 角色 Agent × M（本书角色注册表）
```

这与「一个产品下多个项目，项目下有特有成员」一致：**PM 作为逻辑身份延续**（人设可随阶段变），**切换小说 = 切换项目上下文**，下属 Agent **集合与实例**随书而变。

### 4.3 全局工具（Tools）：供所有智能体调用

以下能力宜抽象为 **Tools**（统一注册、权限与预算），**PM、角色 Agent、范围 Agent、设定研究等**均可按策略调用，**不**绑死在某一类 Agent 上：

| 类型 | 示例 | 说明 |
|------|------|------|
| **记忆搜索** | 渐进式 memory、作者归类记忆检索 | 与本书 `data_root` 绑定；跨书时仅匿名偏好通道 |
| **知识库搜索** | 作品内设定库、大纲/节拍库 | 只读为主，写回走门闩 |
| **互联网搜索** | 设定研究、资料查证 | 可配置开关与配额；结果进入 Assembler，不直写正文 |

**实现备忘（非承诺）**：联网类 Tool 若需**可控浏览器**抓取或交互式取证，技术路线可考虑 **[Playwright](https://playwright.dev/)**（或同类）封装为受控子进程/服务；**当前仓库暂不实现**，仅作文档级预留，避免与现有纯 API 检索方案混为一谈。

**与 Harness**：检索路由（RetrievalRouter）与 **Tool 注册表** 对齐；未来扩展新工具时**只增表项与实现**，不复制多套入口逻辑。

### 4.4 DevAgent：削弱「编码执行」，强化「记录与观察」

- **方向**：弱化「自动改代码 / 替代开发者」的权重；演进为**整体工作的记录者、观察者**——帮助作者**看见**进度、失败、建议任务、与规约/测试的偏差，**便于推进**创作与工程迭代。  
- **与 PM**：DevAgent **不**与作者抢「主对话」；可侧向输出 **WORKLOG / next-iteration / 任务清单** 类产物，由作者或人类开发者决定是否采纳。  
- **与 Tools**：若需跑测试、读仓库，可作为 **受控工具** 挂在自动化层，**默认不**进入作者在环主路径。

## 5. 与现有 Harness / 代码的对应（不强行实现）

| 概念 | 现有/规划中的落点 |
|------|-------------------|
| PM 与作者对话 | `AuthorSession` + `read_line`；未来可把 **phase 策略包**显式命名为「PM 模式」 |
| 意图与路由 | `classify_intent` / 审阅 `understand_author_review_intent` → 扩展为 **多 phase 白名单** |
| 检索与联合记忆 | `retrieve_for_intent`、渐进式 memory、大纲 snippet；**联合记忆**多落在此类只读工具 |
| 角色内置记忆 | `CharacterAgent`、storage 分库；**不与** `intent_retrieval` 混为一谈 |
| 编排 | `Orchestrator`、回合流水线；PM **不替代** Orchestrator，而是**作者在环侧**的「决策与组装」层 |
| 全局 Tools | 记忆搜索 / 知识库 / 联网等，注册表 + 预算；各 Agent 共用（§4.3） |
| DevAgent | 记录、观察、任务沉淀；**不**抢占作者在环主对话（§4.4） |

## 6. 交互与派单（逻辑流程）

1. **作者**对 PM 说话（一句或一段）。  
2. **Harness**：分类 → 是否需要检索联合记忆 / Tool → 组装上下文；**阶段变化**时可切换 PM 对外人格与策略包，**仍**依赖 digest 与本书上下文保持意图连续。  
3. **PM（逻辑）**判断：  
   - 仅要**本书内**专业意见 → 指定 **按需加载的本书能力 / 范围 / 角色** 之一生成（可多轮子调用）；  
   - 要**跨回合一致性** → 读联合记忆 + 相关内置记忆（经权限与预算）；  
   - **匿名跨书偏好**（如用语习惯）→ 仅写入 **§3.3 默认可用** 通道；**非匿名内容**默认不落跨书。  
4. **汇总**为作者可读答复；**写回**仍走现有 **门闩与两阶段审阅**（TECH §6.2）。

**关键原则**：**对作者仍是一个对话主体**；**内部**可多智能体协作，但**不**把内部拓扑强行暴露给作者（除非产品要「开发者模式」）。

---

## 7. 边界与非目标（本方案讨论稿）

- **不**在本方案中承诺「多 Agent 自动并行写百万字无需审阅」——与 [author-in-loop-spec](../specs/author-in-loop-spec.md) 一致。  
- **不**强制立刻实现「独立 PM 模型」；可先 **Harness + 单 LLM 多步** 演进。  
- **角色 Agent** 与 **PM** 的职责混淆是风险：必须明确 **PM 只做编排与呈现，不替代角色内心独白生成**（除非产品明确要「上帝视角」）。

## 10. 已定共识与余留问题

### 10.1 已定共识（本轮）

| 主题 | 结论 |
|------|------|
| PM 人格 | 可**不同阶段换人格**，仍保持 **Harness 统一入口** 与 **意图/上下文延续**（digest、本书状态、匿名偏好）。 |
| 小说管家 | **现阶段不**作为独立常驻智能体；**按需加载**本书级编排与状态能力。 |
| 跨书记忆 | **默认仅匿名偏好**；剧情与可识别内容**不**默认跨书。 |
| DevAgent | **削弱**自动编码主叙事；强化 **工作记录、观察、辅助推进**（与作者在环主对话分离）。 |
| 工具 | **记忆搜索、知识库搜索、互联网搜索** 等抽象为 **Tools**，**所有智能体可按策略调用**（注册表 + 预算）。 |

### 10.2 仍可后续细化（非阻塞）

- 「匿名偏好」的**存储形态**（键、TTL、用户清除路径）与 **WORKLOG** 的衔接。  
- DevAgent 产出物与 **CI / 测试门禁** 的**最低保证**（仅记录 vs 必须过测）。  
- **联网 Tool** 的合规开关与每本书配额；若采用 Playwright 等浏览器自动化，另需 **沙箱、超时、资源上限** 与运维说明（当前不实现）。
